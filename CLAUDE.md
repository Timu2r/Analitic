# auto-builder — Claude Infrastructure

Конвейер: **идея → рабочий прототип (фронт с моками) → деплой на Vercel → проверка идеи (custdev) → план → реализация с QA-контролем**.

Стек прототипов: **Vite + React + TypeScript + Tailwind + shadcn/ui**.

---

## Базовые правила работы (всегда)

Дословные Karpathy behavioral guidelines: **`docs/karpathy-CLAUDE.md`** (применять как есть). Кратко 4 правила:

1. **Think Before Coding** — не угадывай, не прячь сомнения, покажи tradeoffs; не уверен — спроси.
2. **Simplicity First** — минимум кода, без спекулятивных абстракций; 200 строк можно в 50 — перепиши.
3. **Surgical Changes** — трогай только нужное; не рефакторь рабочее; убирай только свой мусор.
4. **Goal-Driven Execution** — определи success criteria, цикл до verified.

Наши дополнения:

### 5. ts-loop (закрытие багов)
Как только баг определён (QA / тест / пользователь): расследовать первопричину → исследовать решения → применить → протестировать на баг → если баг остался, повторить весь цикл до закрытия. Для UI — agent-browser (DevTools) + playwright-mcp + `console.log()` в ключевых точках. См. skill `ts-loop`. Применяют **основной агент И все QA**.

### 6. Objectivity (для всех кто тестирует)
QA — это поиск проблем, а не подтверждение что «работает».
- Тестировать позитивные И негативные кейсы.
- Быть объективным: отчёт о факте + доказательство, не о желаемом.
- Провал теста = сказать прямо с выводом теста.

## Кастомные агенты (`.claude/agents/`)

| Агент | Роль |
|---|---|
| `ui-ux-designer` | Современный UI/UX дизайн, дизайн-система, визуальная иерархия |
| `frontend-developer` | Реализация фронта на Vite+React+TS+shadcn |
| `frontend-qa` | Объективное тестирование UI (позитив+негатив) через playwright-mcp + agent-browser FULLHD |
| `backend-qa` | Объективное тестирование API/логики (позитив+негатив) |
| `qa-team-lead` | Тимлид для Agent Teams: получает крупную QA-задачу, дробит и делегирует своим субагентам |

Правила выбора:
- **Мелкая задача** → основной агент проверяет сам (без делегирования).
- **Средняя задача** → один qa-subagent через Task.
- **Крупная / параллельная** → Agent Teams: поднять `qa-team-lead`, который сам дробит работу на своих субагентов.

## Правила тестирования (subagent + Agent Team + основной агент — все)

Применяется к КАЖДОМУ кто тестирует UI/функциональность:

1. **Браузер:** playwright-mcp и/или agent-browser, размер окна — **FULLHD (1920×1080)**.
2. **Кейсы:** обязательно позитивные И негативные (invalid input, edge cases, broken backend responses, fast clicks, странные viewport-ы).
3. **Объективность:** репортить факты с доказательством (screenshot / console / network log). Не «выглядит ок» — а «кнопка X кликается, форма Y отдаёт 200, при пустом email показывает ошибку Z».
4. **ts-loop:** не останавливаться на первом прогоне — цикл fix→verify пока success criteria не выполнены.

## ts-loop (troubleshooting loop) — обязательное правило

Касается **основного агента и всех QA**. Полное описание: skill `ts-loop`.

Закрытие бага после его обнаружения:
```
1. INVESTIGATE — расследовать первопричину (repro, логи, console.log в ключевых точках,
                 для UI — agent-browser DevTools: Console/Network/Elements/Sources + playwright-mcp)
2. RESEARCH    — исследовать варианты фикса, выбрать минимальный
3. APPLY       — применить surgical-фикс по root cause
4. TEST        — повторить repro, доказать что баг исчез (+ регрессия рядом)
5. Баг остался? → goto 1 (весь цикл заново). Исчез? → закрыть, убрать временные логи.
```
Лимит ~3-5 циклов → если не закрылся, summarize расследование пользователю.

## Workflow (7 этапов)

Полное описание: `docs/WORKFLOW.md`.

1. **Прототип** — рабочий фронт с моками, демонстрирует бизнес-логику и решение.
2. **Деплой** — на Vercel.
3. **Проверка идеи (custdev)** — Reddit + другие платформы; генерим запросы, собираем ссылки, анализируем. Skill `custdev-reddit`.
4. **Обсуждение будущего проекта** — планы, дедлайны.
5. **Как реализовать?** — техническая архитектура фронта/бэка/приложения.
6. **План реализации** — speckit (`/speckit.plan`, `/speckit.tasks`, `/speckit.analyze`) + обязательные QA-персонажи (frontend-qa, backend-qa) для контроля качества, работоспособности, релевантности бизнес-решению.
7. *(зарезервировано — продолжение конвейера)*

## Этап очистки и проверки мок-данных

Перед переходом от прототипа (моки) к реальной реализации — **обязательный** этап. Skill `mock-cleanup`.
- Найти все моки/фикстуры/hardcoded данные.
- Проверить что ни один мок не утёк в "реальные" пути.
- Заменить на реальные источники или явно пометить TODO.

## Speckit (встроенные навыки)

Используем только: `/speckit.plan`, `/speckit.tasks`, `/speckit.analyze`.
- `plan` — на этапе 5-6 (техническая архитектура → план).
- `tasks` — разбить план на задачи.
- `analyze` — кросс-проверка консистентности артефактов перед реализацией.

## Custdev / fact-checking через Reddit

Skill `custdev-reddit`. Reddit заблокирован для WebFetch/Playwright в этой среде.
Рабочие методы:
1. **curl на `.json` endpoints** через Bash (основной).
2. **Полуручной**: агент пишет поисковые запросы → пользователь запускает в браузере → отдаёт ссылки/данные → агент анализирует.
